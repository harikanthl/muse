# Prior art: muse_decode_layer and muse_prefill_layer (fusion, megakernels, 4-bit prefill)

Research agent report, collected 2026-10-31 (web sources, verified unless flagged inside). Part of the Open Kernel Challenge notes; see ../moe-field-guide.md for the synthesis.

All findings below were checked against primary sources (blog/paper/GitHub via `gh api`) unless marked UNVERIFIED.

**Q1 Megakernels (decode)**
- Hazy "No Bubbles" (https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles; code https://github.com/HazyResearch/Megakernels, verified exists): on-GPU interpreter, per-SM instruction list pre-scheduled in Python; deps = zero-initialised global counter array (producer increments, consumer spins to target; MLP intermediate split into 4 chunks with own counters so down-proj waits only on its chunk); smem split into 13×16 KiB pages that instructions request/release so the next instruction's weight loads start during the previous epilogue. Llama-1B BF16 batch 1: ~78% HBM BW on H100, 2.5× vLLM / >1.5× SGLang (both with CUDA graphs). Dense only, batch 1 only. ThunderMLA (https://hazyresearch.stanford.edu/blog/2025-03-04-thundermla) is the attention-only precursor: 20–35% over FlashMLA.
- Cohere megakernel (https://cohere.com/blog/megakernels; https://github.com/cohere-ai/cohere-megakernel, verified, single CUDA file, SM90a, BF16, batch 1–8): 30B/3.3B-active MoE. Static: host builds per-layer waves, deals task k to SM k mod 132. Dynamic: attention tiles and MoE expert tiles go into shared atomic work queues; ROUTER_GEMM→ROUTER_TOPK→ROUTE_FINALIZE builds the MoE queue inside the kernel. Global-memory integer barriers with fences. Dependency-affinity placement was 1–2% slower than round-robin. 1.58× vLLM at B=1 (62% of speed-of-light vs 39%), 1.32× at B=8/8K ctx with real routing (1.14× uniform). They rank wave quantization, false dependencies and weight prefetch above raw launch overhead.
- MPK (https://arxiv.org/abs/2512.22219, v2 June 2026; code mirage-project/mirage): compiler + in-kernel runtime; fixed worker SMs (128 on H100) with FIFO circular queues + 16 scheduler warps on 4 SMs; event fusion cuts deps 37–118×. Qwen3-8B: 293 launches/token → 1 (they measure 3.8 µs/launch eager, 0.8 µs under CUDA graphs). 1.0–1.7× over best of vLLM/SGLang single GPU. MoE: hybrid static expert partition + runtime meta-tensor splitting beats static; the separate gather is up to 11% of SGLang MoE time at B=1 so they fold gather into GEMM loads.
- MonoMoE (https://arxiv.org/html/2609.04244v1): VERIFIED code exists at flashinfer `csrc/fused_moe/monomoe/` (monomoe_binding.cu, monomoe_wrapper.cuh, src/{moe_up_projection,moe_down_projection,moe_routing,moe_tma,...}.cuh) and `flashinfer/fused_moe/monomoe.py`. Caveats: hard-specialised to E=256, N=512, K=2048, M≤8, block-FP8 128×128 weights — not NVFP4, not Muse shapes. Design is reusable: "weight-major" CTA stripes over expert weights with tokens on the N side (SwapAB, N=8 WGMMA), router+topk+quant+up+SwiGLU+down+atomicAdd reduction fused, readiness flags, one CTA/SM. 1.17–1.54× vs vLLM Triton grouped GEMM on H200 at B=1–8; no hot-expert handling.

**Q2 Cheaper than megakernel**
- SGLang's Muse Spark model already does the side-stream router (sglang `python/sglang/srt/models/muse_spark.py` ~L800–850: `side_stream.wait_stream(main)`; router GEMV (CuTeDSL) + fused sigmoid/bias top-k on side stream; join before experts) and uses fused QK-norm+RoPE+KV-store, FusedRMSNormGate, fused post-norm+residual-gate+next-pre-norm "boundary" kernels, post-expert finalize (Triton). So the ~20-kernel baseline is already fused at those seams.
- Triton PDL: VERIFIED. `tl.extra.cuda.gdc_wait()` / `tl.extra.cuda.gdc_launch_dependents()` and host `kernel[grid](..., launch_pdl=True)` (triton/python/tutorials/11-programmatic-dependent-launch.py; docs https://triton-lang.org/main/python-api/triton.language.extra.cuda.html). SM90+. gdc_launch_dependents gives no memory ordering.
- Measured per-launch: ~2.1 µs/launch on-stream, ~1.3 µs with CUDA graphs on H100 (https://mohakchugh.is-a.dev/blog/megakernels-single-launch-llm-inference-eliminating-kernel-boundaries); PDL moves the next kernel start from ~1 µs after to ~0.25 µs before the previous end (https://jonahsamost.bearblog.dev/pdl-and-tvm-ffi/). No framework-level Hopper PDL benchmark found (UNVERIFIED gains). FlashInfer uses enable_pdl widely (PRs #6449, #6605, #7641 etc.).

**Q3 Prefill 4-bit MoE on Hopper**
- CUTLASS ex. 55 + ex. 69 (`examples/69_hopper_mixed_dtype_grouped_gemm`, int4×bf16 grouped): narrow operand through registers, upcast, wgmma; documented narrow types int2/int4/int8 (+fp8×int4). Scale group size must be K or a multiple of tile-K (`sm90_mma_tma_gmma_rs_warpspecialized_mixed_input.hpp` L484) — so NVFP4 group-16 E4M3 scales do NOT fit directly; grouped version only supports row-wise, or group-wise with identical problem shapes. E2M1 on SM90 mixed-input: not documented (code search found none) — UNVERIFIED/likely needs a custom e2m1→bf16 converter.
- Machete (https://developers.redhat.com/articles/2024/10/14/introducing-machete-mixed-input-gemm-kernel; vllm csrc/quantization/machete): int4/int8 only, no fp4 (code search 0 hits). Claims Marlin's mma.sync loses ~37% of Hopper peak; Machete ≈FP16 speed at M≥128. No TFLOP/s table in text.
- Marlin NVFP4 (sglang `moe_wna16_marlin.cuh`): has kFE2M1f with group_blocks==1 (group 16, E4M3 scales) — this is the baseline; no wgmma in that file.
- FlashInfer: `cake_w4a16.py` is exactly BF16×NVFP4 (E2M1 + E4M3/16) in-kernel dequant MoE — but sm_100a/103a only. v0.6.18 notes mention "W4A16 runners on SM90" in the unified MoE API (format unverified, likely MXINT4/MXFP4 via cutlass_backend).
- DeepGEMM: SM90 FP8 only (FP32 scales); FP8×FP4 and Mega MoE are SM100. Cohere W4A8 grouped GEMM for Hopper (vLLM PR #29691, INT4+FP8 LUT dequant, https://cohere.com/blog/vllm-integration-and-quality-recovery-techniques-explained) — changes activation dtype, so likely rule-incompatible.
- TileLang has FP4(E2M1)×FP16 dequant-GEMM examples (arXiv 2504.17577); H100 numbers unverified.

**Q4 Skewed routing**
- CUTLASS grouped scheduler: round-robin tiles, equal tiles per CTA regardless of active tiles (https://docs.nvidia.com/cutlass/4.4.1/media/docs/cpp/grouped_scheduler.html). DeepGEMM masked grouped GEMM: M-grouped, fixed N/K, computes only `masked_m` rows (CUDA-graph safe). MPK: hybrid static+runtime split; Cohere: atomic queue. ExpertPlex (arXiv 2607.18002) tile-level scheduling, <10% overhead. LPT / Stream-K-across-experts: NOT FOUND in any source.

**Q5 Fusions** — FlashInfer `fused_add_rmsnorm(_quant/_fp8_block_quant)`; vLLM HPC `rope_norm` (RoPE+QK-norm+KV write+FP8). No published GEMM-epilogue KV-cache write found. SGLang Muse already has these fused.

**Q6** — Only MonoMoE (block-FP8, Hopper) and Cohere (BF16) report vs vLLM; none use NVFP4 on Hopper. Alpha-MoE (FP8 W8A8, archived) — unverified "200%".

**Top 5 decode_layer ideas**: (1) Cohere-style persistent kernel for the MoE block only (router→topk→queue→weight-major NVFP4 expert tiles→atomic reduce) with global counters, weight-major like MonoMoE so T=1 streams 8×28 MB at full BW; (2) PDL (Triton `launch_pdl` or CUTLASS GDC) on every remaining boundary + capture in one graph; (3) MPK-style fold of the gather/permute into expert GEMM loads; (4) prefetch next op's weights (pooler/unpooler) into L2/smem during spin-waits; (5) fuse pooler GEMM + pre-expert norm and unpooler into the finalize.

**Top 3 prefill_layer**: (1) CUTLASS ex. 69 mixed-input grouped GEMM with a custom E2M1→BF16 register converter and group-16 scales applied in the converter (not the collective's scale path); (2) persistent tile scheduler with masked/per-expert tile counts and atomic queue (hot experts first); (3) fuse SwiGLU + unpooler input prep in epilogue, keep BF16 activations.

**Dead ends**: MonoMoE code as-is (fixed shape, FP8); FlashInfer cake_w4a16/DeepGEMM FP4/Mega MoE (SM100 only); Machete (no FP4); Cohere W4A8 (FP8 activations); CUTLASS grouped group-wise scaling for non-identical shapes; LPT/Stream-K-across-experts prior art not found.
